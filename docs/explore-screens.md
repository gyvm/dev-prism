# Explore 画面仕様

Explore の各ページが「何を確認するための画面か」「何をどう表示するか」を定義する。
実装計画・アーキテクチャは `explore-views-plan.md`、数値定義は `glossary.md` を参照。

## 全体像

Explore は「チームの開発フローを、問いの単位で切ったページ」の集合。
1ページ = 1つの問いに答える構成とし、要素を足すときは「どのページの問いに属するか」で置き場所を決める。

### 画面レイアウト

全ページ共通の枠組み。最上部にフィルタバー、その下にページ切り替えタブ、タブの下にページ本体。
ページ本体は各ページの「表示内容」の表の順に上から縦積みで表示する。

```
┌──────────────────────────────────────────┐
│ フィルタバー: 期間 │ リポジトリ │ メンバー │ bot切替 │
├──────────────────────────────────────────┤
│ タブ:  フロー │ レビュー │ タイムライン │ 滞留       │
├──────────────────────────────────────────┤
│                                          │
│  ページ本体(要素を表示順に縦積み)              │
│                                          │
└──────────────────────────────────────────┘
```

### タブ順序 — 確認のストーリー

タブは週次振り返りのアジェンダ順。「数字で総括 → プロセスを検査 → 具体例に降りる → 次のフォローを決めて締める」。

| 順 | タブ | URL | 答える問い | 時間軸 | ストーリー上の役割 |
|---|---|---|---|---|---|
| 1 | フロー | `/explore/flow/` | 変更は速く・安定して main に届いているか | 過去(遅行指標) | 数字で総括する。振り返りの入口 |
| 2 | レビュー | `/explore/review/` | レビューは機能しているか、負荷は偏っていないか | 過去(遅行指標) | プロセスを検査する |
| 3 | タイムライン | `/explore/timeline/` | 振り返りで拾うべき PR はどれか | 過去(個別事例) | 集計の異常を具体例に降ろす |
| 4 | 滞留 | `/explore/wip/` | **今**止まっているものは何か | 現在(先行指標) | 来週のフォローアップを決めて締める |

旧称「PR個別」は URL に合わせて「タイムライン」に統一する。

### フィルタバー

- **期間(PeriodPicker)**: フロー / レビュー / タイムラインに適用。**滞留には適用しない**
  (滞留は現在のスナップショットを見る画面のため。適用すると「先週作成されたオープン PR だけ」の
  ような誤読を生む)。滞留タブ選択中は無効化表示にする
- **リポジトリ / メンバー(MultiSelect)**: 全ページに適用
- **bot トグル**: bot(AI レビュー・bot 作成 PR)を計測に含めるかの切り替え。**デフォルトは除外**、
  トグルで含める。actor kind(human / bot)はデータ層で判別済みのため実装可能。
  これにより従来「⏸ bot方針待ち」だった要素は解禁される(方針決定は「含めるか否か」から
  「デフォルトをどちらにするか」に格下げされた)
- フィルタ状態はクエリパラメータで保持し、タブ間遷移で引き継ぐ

### データと数値の方針

- データは DuckDB-WASM による parquet ライブクエリ。集計定義は凍結レポートと同一の query 関数を
  共有する(数値の parity)
- **低サンプル方針**: 数値カードには母数 n を併記する(週次 × フィルタで n が数件になると率・p50 は
  激しく振れるため)。変更障害率 / MTTR は「Revert 0件(n=X)」と「データなし」を表示で区別する
- **進行中期間の前期間比較**: 選択期間が進行中(例: 今週3日目)の場合、同じ長さの直前期間との
  比較は常に悪化して見えるため、前期間比較は表示しない

### ページ間の動線

集計 → 具体例へ降りる遷移を一級の要素として定義する。遷移時はフィルタ状態を引き継ぐ。
新しい要素を足すときは「どの動線上にあるか」も確認する。

| 起点 | 操作 | 遷移先 |
|---|---|---|
| フロー 1-2 ファネルのステージカード | クリック | タイムライン 3-2 テーブルを当該ステージ時間の降順ソートで開く |
| レビュー 2-3 散布図の点 | クリック | 当該 PR の GitHub ページ |
| タイムライン 3-1 / 3-2 の PR | クリック | 当該 PR の GitHub ページ |
| 滞留 4-2 エイジングテーブルの行 | クリック | 当該 PR の GitHub ページ |

## 1. フロー (`/explore/flow/`)

### 目的

変更が main に届くまでの**速さと安定度**を確認する。週次振り返りの入口。

これを見るとわかること:

- 先週のチームは速かったか・遅かったか(前期間との比較)
- 遅かった場合、**どのステージ**(コミット→オープン→レビュー→アプルーブ→マージ)が詰まったか
- 生産のリズム(PR の作成・マージ量)が安定しているか

### 表示内容(上から表示順)

「サマリ → 分解 → 時系列」の順。1-1 が「遅い」と言い、1-2 が「どこが」に答え、1-3 が「いつから」を示す。

| # | 要素 | 形式 | 目的 | 状態 |
|---|---|---|---|---|
| 1-1 | DORA メトリクスカード + 前期間比較 | 数値カード ×4 横並び(白地・スリムアクセントボーダー)。カード内に増減矢印 + 差分値(例 `↘ -0.8件`)と n を併記 | チームの健康状態の一次サマリ。デプロイ頻度(=マージ PR 数)、リードタイム p50、変更障害率(Revert 検知)、MTTR。比較対象は同じ長さの直前期間(進行中期間では比較非表示) | ✅ カード実装済 / 🆕 前期間比較 |
| 1-2 | サイクルタイムファネル | 横並びステージカード(コミット→オープン / オープン→レビュー / レビュー→アプルーブ / アプルーブ→マージ)。各ステージ p50 | 合算リードタイムを分解し、**ボトルネックのステージを特定**する。**合計値は表示しない**(p50 は加算不能で 1-1 のリードタイム p50 と一致しないため。合算の代表値は 1-1 に委ね、ここはステージ間の相対比較専用)。ステージカードクリックで 3-2 へドリルダウン | 🆕 追加 |
| 1-3 | リードタイムの推移 | 折れ線(ステージ別 p50、1-2 と同じ分解) | 1-2 のスナップショットに対し、悪化・改善の**向き**を時系列で示す。ファネル直下に置き、同じ分解の時系列版として読ませる | 🆕 追加 |
| 1-4 | PR 件数の推移 | 折れ線(作成 / マージ、日次・週次) | 生産の量とリズムの把握。谷や山を振り返りの話題にする | ✅ 実装済 |

## 2. レビュー (`/explore/review/`)

### 目的

レビューが**機能しているか**(素通しになっていないか)と、レビュー負荷が**偏っていないか**を確認する。

問いが2つあるため、ページ内を2つのブロックに分ける。バックログの「手戻り」はブロック A に
属するため、実装時にはページ分割(A / B を別タブ化)を再検討する。

これを見るとわかること:

- レビューを経ずにマージされた変更がどれだけあるか
- PR サイズがレビューの速さを損なっていないか
- レビューの負荷が誰に集中しているか(bot トグルで人間 / AI の構図も見られる)

### 表示内容(上から表示順)

**ブロック A: レビューは機能しているか**

| # | 要素 | 形式 | 目的 | 状態 |
|---|---|---|---|---|
| 2-1 | レビューなしマージ | 数値カード ×1(率 + 件数 n 併記) | レビュープロセスの素通り検知。`first_review_at` の null 率から算出。分母はマージ済み PR。旧案の「レビュー実施率」カードは補数(足して100%)のため置かない。bot トグルの影響を最も受ける指標(AI レビューを含めると率が下がる) | 🆕 追加 |
| 2-2 | レビュー・コメント件数の推移 | 折れ線(レビュー / コメント) | レビュー活動量の増減。件数スケールが PR 系と桁違いのため独立チャート | ✅ 実装済 |
| 2-3 | サイズ × レビュー着手の散布図 | 散布図(X: オープン→レビュー時間、Y: 変更行数・対数スケール) | 「大きい PR ほどレビューが遅い」の実態確認。右上の点が改善対象(PR 分割の根拠になる)。点クリックで GitHub へ | 🆕 追加 |

**ブロック B: 負荷は偏っていないか**

| # | 要素 | 形式 | 目的 | 状態 |
|---|---|---|---|---|
| 2-4 | レビュー相関 | 二部グラフ(作成者 ⇄ レビュアー) | 誰が誰をレビューしているかの構図と負荷の偏りを、**序列を付けずに**見せる(個人ランキングは採用しない)。bot トグル ON で AI レビュアーを含む構図も確認できる | ✅ 実装済 |
| 2-5 | レビュアー別リードタイム | 横棒グラフ(依頼→レビューまでの平均時間 / レビュアー) | レビュー依頼への応答が滞っている箇所の特定 | 🆕 追加(bot トグルにより解禁) |

## 3. タイムライン (`/explore/timeline/`)

### 目的

個々の PR の生涯を眺め、**振り返りで拾うべき PR**(外れ値・異常な形)を特定する。
フロー / レビューが集計値で「何かおかしい」と言ったとき、ここで具体例に降りる。
フロー 1-2 ファネルからのドリルダウン着地点。

これを見るとわかること:

- 各 PR がどのステージでどれだけ時間を使ったか(帯の形)
- 期間内で突出して遅かった / 大きかった PR はどれか

### 表示内容(上から表示順)

「視覚で当たりをつけ、表で確定する」の順。

| # | 要素 | 形式 | 目的 | 状態 |
|---|---|---|---|---|
| 3-1 | PR タイムライン | ガントチャート(1 行 = 1 PR、ステージ別に色分けした帯) | 帯の**形**で異常を見つける(レビュー待ちが長い帯、マージ直前で止まる帯など)。視覚的パターン認識用 | ✅ 実装済 |
| 3-2 | ステージ別時間テーブル | テーブル(PR・変更行数・各ステージ時間・マージ日)。各カラムでソート可能。ソートキーをクエリパラメータで受け、ファネルからのドリルダウンで当該ステージ降順の状態で開く | 数値での外れ値特定。「オープン→レビューが最長だった PR」をソート 1 回で取り出し、振り返りの具体題材にする。3-1 と同一データの表形式 | 🆕 追加 |

マージされず閉じた PR(`closed_unmerged`)の表示は、バックログ「捨てられた仕事」と同時に判断する。

## 4. 滞留 (`/explore/wip/`) — 新規ページ

### 目的

**今**止まっているものを見つける。他ページが完了 PR の事後分析(遅行指標)なのに対し、
このページだけが「これから問題になるもの」を指す先行指標を扱う。週次 MTG の
「フォローアップ候補」の供給源として、タブの最後に置き会議の締めに使う。

**期間フィルタは適用しない**(現在のスナップショット。フィルタバー参照)。

これを見るとわかること:

- 長期間オープンのままの PR(忘れられた仕事)
- レビュー依頼済みなのに着手されていない PR(詰まっている場所)
- アプルーブ済みなのにマージされていない PR(あと一歩の仕事)

### 表示内容(上から表示順)

| # | 要素 | 形式 | 目的 | 状態 |
|---|---|---|---|---|
| 4-1 | 滞留サマリ | 数値カード ×3(オープン PR 数 / レビュー待ち数 / 最古 PR の経過日数) | 滞留の総量を一目で把握。最古経過日数は「放置の上限」を示す代表値 | 🆕 追加 |
| 4-2 | エイジングテーブル | テーブル(PR タイトル・作成者・状態・**ボール保持者**・経過時間・最終更新)。経過時間降順、状態バッジ(ドラフト / レビュー待ち / 変更依頼中 / アプルーブ済み未マージ)。PR タイトルは GitHub へリンク | 個々の滞留 PR を特定し、その場で「誰が拾うか」を決められるようにする。ボール保持者は状態から導出する: レビュー待ち→依頼先レビュアー、変更依頼中→作成者、アプルーブ済み→作成者。序列ではなく担当の明示のため、個人ランキング不採用の原則とは矛盾しない | 🆕 追加 |
| 4-3 | 経過時間の分布 | ヒストグラム(経過時間帯別のオープン PR 件数) | 滞留が慢性的(分布が右に厚い)か一時的(直近に集中)かの判別 | 🆕 追加(優先度低) |

## 実装優先度

🆕 要素のうち、**1-2 ファネルと 3-2 テーブルは同一イテレーションで実装する**。
両者が動線で繋がって初めて「集計 → 具体例に降りる」体験が完成するため。
それ以外は各ページ内の表示順に準じ、4-3 は優先度低。

## 将来候補(バックログ)

ページ化はせず、方針決定または需要の確認を待つもの。

| 候補 | 問い | 前提 |
|---|---|---|
| AI 分業 | AI 導入はフローをどう変えたか(bot PR 比率・マージ率・人間 oversight 率) | bot トグルで暫定対応済み。独立ページ化は需要の確認待ち |
| 手戻り | 一発で通ったか(初回レビュー後のコミット数・CHANGES_REQUESTED 往復・スレッド未解決マージ率) | bot トグルで解禁可能。レビューページのブロック A 拡張、混みすぎるならページ分割 |
| 捨てられた仕事 | マージされずクローズされた PR とそのコスト | データは揃済。滞留ページへのタブ追加が候補(タイムラインの `closed_unmerged` 表示と同時判断) |
| ホットスポット | どのファイルにリスクが集中しているか(`pr_files` × スレッド密度 × Revert) | 四半期粒度。週次 Explore とは別リズム |
| ラベル別時間配分 | feature / bugfix / chore の構成比 | ラベル運用の規律。付与率を実データで確認してから |
| 時間帯・曜日分布 | 持続可能なペースか(深夜・休日比率) | チーム集計に限定(個人単位では出さない) |

## 設計上の決定事項

- **個人ランキングは採用しない**。メンバー別トップ 5・増減メンバー表(Findy Team+ のレポート画面)は、
  チームのフローを映すという dev-prism の目的とズレるため見送り。負荷の偏りはレビュー相関(2-4)で
  序列なしに見せる。滞留のボール保持者列(4-2)は序列ではなく担当の明示であり例外としない
- **bot はデフォルト除外、トグルで含める**。「bot を計測に含めるか」の二値決定を待たず、
  デフォルト除外 + フィルタバーのトグルで両方見られるようにする(⏸ 状態の解消)
- **p50 は加算しない**。ステージ別 p50 の和は合計 p50 と一致しないため、ファネル(1-2)に合計値を
  置かず、合算の代表値は DORA カード(1-1)のリードタイム p50 に一本化する
- **イシュー系・実デプロイ系メトリクスは扱わない**。収集対象が PR のみであり、DORA は「マージ = デプロイ」
  プロキシで一貫させる
- **土日祝・就業時間外の除外は当面行わない**。全リードタイム計算を横断する変更のため、
  導入するなら独立したイテレーションで判断する
